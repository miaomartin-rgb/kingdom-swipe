保留

30 KB、零外部資產、開啟即玩。Poki 要求首次下載 < 8 MB，CrazyGames 手機首頁位要求 < 20 MB — 你目前用掉配額的 0.4%。這是網頁通路上罕見的結構性優勢，任何升級都不該犧牲它。

必修

經濟迴圈。閘門給指數收入、雜兵團收線性成本、Boss 血量又反過來綁定兵力。三者疊加的結果是：第 6 關兵力達 3,690 萬，而雜兵團的損耗只佔 0.002%。玩得好與玩得爛，結局相同。

轉向

從 hyper-casual 走向 hybrid-casual。純 hyper-casual 的 D30 留存已低於 4%，而 hybrid-casual 的 LTV 是其 3–5 倍。目前專案沒有存檔、沒有進度、沒有任何變現掛載點 — 這三樣是同一件事的三個面向。

§ 1現況架構

整個遊戲是一個 IIFE，全部狀態集中在單一全域物件 G，透過 update(dt) 與 render() 兩個函式在同一個 requestAnimationFrame 迴圈裡推進。 渲染是 Canvas 2D 手刻的偽 3D 投影 — scaleAt(z) 算縮放、px()/py() 投影， 再用畫家演算法由遠而近排序繪製。沒有引擎、沒有建置流程、沒有任何外部資產。

真正值得保護的三件事

  1. 載入體積。30 KB 純文字，冷啟動幾乎沒有等待。這直接決定了通路上架的難易度，也直接決定了廣告素材（playable ad）的可行性。
  2. 零資產管線。士兵、Boss、天空、音效全部是程式碼生成的。沒有美術外包依賴，改配色只要改常數。
  3. 投影數學是對的。screenToRoad() 用玩家平面的縮放做反投影，拖曳手感與畫面一致，這部分不需要動。

Boss 血量綁定兵力，讓前面所有成長歸零

index.html:653 — b.max = Math.max(b.base, Math.round(G.army*12));

進入王戰的瞬間，Boss 的血量被重新設定為玩家當前兵力的 12 倍；同時傷害輸出是 G.army * 6 * dt。兩者相除，戰鬥時間恆等於 2 秒左右，與兵力多寡無關。 唯一的變數是「兵力是否超過 base 門檻」— 超過就贏，沒超過就輸，中間沒有灰階。

指數收入對線性成本：第 4 關之後數字失控

index.html:141–151（makeOp）· 630–645（雜兵團結算）· 188（過關繼承）

閘門提供 ×2／×3（好結果中佔 45%），而雜兵團的結算是 G.army -= d; q.count -= d; — 雙方扣掉相同的絕對值。 也就是說清掉一個 40 人的雜兵團，永遠只花 40 人，不管你帶了 50 還是 5,000。 收入端是乘法、成本端是減法，這個結構必然發散。

第 8 關的 86 億會以 8618571573 的形式塞進 Math.min(52, W*0.13) 的字級裡橫向溢出畫面。 更關鍵的是：第 6 關之後，遊戲裡所有的「威脅」加總不到兵力的萬分之一。

建議修法：把成本改成比例制，把乘法變稀有

  • 雜兵團改為百分比損耗。lost = army * (squadPower / (army + squadPower)) — 帶得多仍然佔優（存活比例高），但永遠有代價，成本不會歸零。
  • 乘法閘門稀有化。把 ×2 的出現率從 45% 降到 15–20%，每關至多 2 個，其餘改為加法與百分比（+30%）。加法為主的經濟成長是多項式而非指數。
  • 過關繼承改為固定值。目前 Math.max(35, carry*0.45) 會把爆炸值帶進下一關。改成 min(carry*0.45, baseByLevel(lv))，每關從可控的起點重新開始爬。
  • 數字格式化。超過 10,000 顯示 1.2萬／3.4M，避免 HUD 溢出。

同類型頭部產品（Count Masters 一系）的張力來自「×2 好還是 +30 好， 取決於我現在有多少人、後面還有幾個障礙」。本專案把這個問題換成了「綠色還是紅色」。

建議修法：三種讓選擇重新變成選擇的做法

  1. 兩邊都是好處，但要看情境。取消「壞門」，改為 ×2 vs +45 的組合。 當兵力低於 45 時加法較優、高於則乘法較優 — 交叉點會隨著遊戲進行不斷移動，玩家必須真的看自己的數字。 這是最小改動、最高收益的一步。
  2. 風險 / 報酬合約。×3 但下一個雜兵團規模翻倍；+20 但沿路清空障礙。 在門上就把代價標示清楚，讓玩家自己決定要不要賭。
  3. 兵種閘門。劍士 / 弓手 / 盾兵，對雜兵團與 Boss 的效率不同（例如弓手打 Boss 加成、盾兵過雜兵團損耗減半）。 操作完全不變（還是左右拖曳），但決策深度立刻上一個量級，同時也自然打開了 meta 層的升級標的。
順帶一提：閘門判定用的是 G.x < 0 ? o.left : o.right — 只看隊伍中心點。 但 130 人的隊形半徑約 3.3 個世界單位，接近半條車道。玩家會看到半數士兵明明穿過了左門， 結算卻算右門。同類產品的做法是讓群體真的依位置分裂，兩邊分別結算再合併 — 這同時解決了判定爭議，也是一個很強的視覺賣點。

沒有存檔：關掉分頁即歸零

全檔 localStorage 出現次數 = 0 · G.best 僅存在於記憶體（L134）

最高紀錄、關卡進度、靜音設定全部隨頁面卸載消失。以留存的定義來說， 這個遊戲的 D1 留存在結構上不可能存在 — 回訪的玩家看到的是一款他沒玩過的遊戲。 對照市場基準的 D1 中位數 26%、及格線 35%，這不是調校問題，是缺一個 20 行的模組。

這也是為什麼「存檔、進度、變現」我在開頭把它們算作同一件事： 沒有持久化狀態，就沒有 meta 進度可言；沒有 meta 進度，獎勵式廣告就沒有東西可以獎勵。 整條 hybrid-casual 的鏈條都掛在這個檔案上。 

// save.js — 這是整份報告裡投報率最高的 20 行
const KEY = 'kingdom.v1';
const DEFAULTS = { best:0, maxLevel:1, gold:0, upgrades:{}, muted:false, runs:0 };

export function load(){
  try { return { ...DEFAULTS, ...JSON.parse(localStorage.getItem(KEY) ?? '{}') }; }
  catch { return { ...DEFAULTS }; }          // 隱私模式 / 配額滿時安靜退回預設
}
export function save(patch){
  const next = { ...load(), ...patch };
  try { localStorage.setItem(KEY, JSON.stringify(next)); } catch {}
  return next;
}

群體渲染上限 130，成長的爽感在第 2 關就封頂

index.html:307 const n = Math.min(count, 130); · 245–247 crowdRadiusMul 上限 1.45

這類遊戲的多巴胺來源就是「人變多」的視覺回饋。但目前無論兵力是 130 還是 1,300 萬， 畫面上都是 130 個小人、半徑倍率封頂在 1.45。玩家最強烈的成就感訊號，在第 2 關之後就永久失效了。

同時這也是效能瓶頸的所在：drawUnit 每個士兵約 8–10 次 Canvas 路徑操作 （陰影橢圓、雙腿、圓角身體、腰帶、頭、頭盔弧、武器線），玩家與敵軍同框時逼近 2,600 次路徑操作／幀；drawCrowd 還每幀為每個群體配置新陣列並排序。 低階 Android 會在此掉幀。

建議修法：一石二鳥的 LOD + 精靈圖

  • 預繪精靈。啟動時把士兵以 6–8 個尺寸級距（如 4/8/16/32/64 px）各繪製 2–3 個走路影格到離屏 canvas， 執行期改用 drawImage。單兵成本從 ~10 次路徑操作降為 1 次 blit，實測量級可省 5–10 倍。
  • 三段 LOD 讓成長重新可見。近處畫 60 個完整精靈；中距畫 200 個 2×3 px 色塊； 遠處用一張「人海」貼圖，其寬度與 log(兵力) 成正比。這樣 1,300 人和 130 人看起來就會有差別， 而總繪製成本反而下降。
  • 快取漸層。目前 9 處逐幀 createLinearGradient／createRadialGradient。 除了尺寸相依的以外，全部在 resize() 時建立一次即可。
  • 粒子物件池。G.parts 目前逐幀 push／splice，改為固定長度陣列 + 存活旗標。

其他應一併處理的項目

  • 音訊無法復原。AudioContext 在 pointerdown 建立（L212）但從未呼叫 .resume()。iOS 上分頁切換後 context 進入 suspended 就永久靜音。修法：每次使用者互動時 if(actx.state==='suspended') actx.resume()。
  • 沒有 visibilitychange 處理。切回分頁時 last 仍是舊時戳；雖然 dt 有 0.05 上限擋住了，但應該明確暫停並在回來時重置計時。
  • window.__game = G（L801）對外暴露。開發便利，但上架通路或做排行榜前必須移除或以建置旗標包起來。
  • 色覺無障礙。閘門的好壞主要靠綠 / 紅區分，約 8% 男性受影響。×／÷ 符號提供了部分冗餘，但應再加形狀差異（例如好門用實線框、壞門用鋸齒框）。若採用 P0·3 的「兩邊都好」方案，此問題自然消失。
  • 沒有 PWA manifest / Service Worker。30 KB 的遊戲離線可玩幾乎是免費的，且能加入主畫面。
  • 沒有 Open Graph / 分享中繼標籤。網頁遊戲的自然傳播全靠這個。
  • 勝利後有 700 ms 空窗。win() 在 700 ms 後才切換 G.state（L774），期間玩家隊伍會繼續往前跑出關卡尾端。應在擊殺瞬間就凍結推進。
  • HUD 畫在 Canvas 裡。短期沒問題，但 meta 層（升級樹、商店、通行證）用 DOM 迭代會快得多。建議 HUD 逐步搬到 DOM 疊層。

§ 4架構升級：讓數值可以被測試

本報告所有數字都來自我另外手寫的模擬器 — 因為現有程式碼無法在沒有 canvas 的情況下跑。 這正是問題所在：一個以數值為核心的遊戲，卻沒有辦法自動驗證數值。這是拆分模組最實際的理由， 不是為了「架構好看」。

建議的檔案切分

維持零建置（原生 ES modules，瀏覽器直接載入），只在需要壓成單檔上架時跑一次 esbuild。 不要引入 3D 引擎 — 那會直接摧毀 30 KB 的通路優勢，見 § 9。 

src/
  balance.js      // 所有數值常數集中於此。目前散落在 8 個函式裡的魔術數字全部搬進來
  sim.js          // 純函式：(state, input, dt) → state。無 DOM、無 canvas、可在 Node 執行
  levelgen.js     // 帶種子的關卡生成（可重現 → 可回歸測試、可做每日挑戰）
  render/
    scene.js      // 地面、天空、閘門、Boss
    crowd.js      // 精靈圖預繪 + 三段 LOD
    hud.js        // 逐步遷移到 DOM
  meta/
    save.js       // localStorage 持久化
    upgrades.js   // 永久升級樹
    economy.js    // 金幣產出與定價
  platform/
    adapter.js    // 統一介面：showRewarded() / gameplayStart() / gameplayStop()
    poki.js  crazygames.js  none.js   // 各通路實作，一份程式碼多處上架
  analytics.js
test/
  balance.test.js // 八關 × 300 次模擬，斷言兵力曲線落在預期區間

三個非結構性但關鍵的改動

  1. 固定步長累加器。目前戰鬥結算直接乘 dt，在 30 fps 與 144 fps 的裝置上結果會有微小差異。 改為固定 1/60 步長 + 累加器，模擬變得可重現，也才有辦法做回放與防作弊。
  2. 帶種子的隨機。把 Math.random() 換成 mulberry32 之類的 PRNG。 同一個種子產生同一關 — 這是回歸測試、每日挑戰、以及「和朋友比同一關」這類社交鉤子的共同前提。
  3. 數值全部進 balance.js。目前調一次難度要改 makeOp、makeSquad、 buildLevel、startLevel、以及 update() 裡的王戰段落五個地方。 集中之後，配合上面的測試，調校一輪從半小時降到一分鐘。

§ 5Hybrid-casual 化：留存從哪裡來

市場資料指出玩家通常在第 3–5 次 session 需要碰到進度、解鎖或收集系統，通行證則多在 D3–D7 開放。 以下是對應到本專案的最小可行 meta 層 — 刻意保持小，因為 meta 層失敗的常見原因是一次做太多。

最小 meta 層
系統內容開放時機作用的指標
金幣 過關依「殘存兵力 × 關卡」產出，是唯一的軟貨幣 第 1 關結束 建立第一個進度感
永久升級 起始兵力 · 雜兵團損耗減免 · Boss 傷害 · 金幣產出，各 10 級 第 2 關結束 D1 → D3。給「明天再來」一個具體理由
兵種解鎖 劍士（預設）→ 弓手 → 盾兵 → 騎兵，以關卡進度解鎖 第 3、6、10 關 同時餵養 § 3 的閘門深度與收集慾
每日挑戰 固定種子的單關，全球同一關，記錄最佳兵力 D2 起 回訪動機。技術前提是 § 4 的帶種子 PRNG

前 30 秒

市場對 hyper/hybrid-casual 的判定幾乎在前 30 秒完成。目前的開場是一段文字說明加一顆「出征」按鈕， 之後 3.2 秒的拖曳提示。建議改成：

  1. 不要開場選單。直接進第 1 關，隊伍已經在跑。標題與說明改成疊在遊戲畫面上的第一個閘門旁提示。Poki 的「一鍵即玩」要求也指向同一件事。
  2. 第一個閘門必為 ×2 且必在玩家當前所在側。先給一次無條件的成功。
  3. 第二個閘門是真正的選擇（×2 vs +45），並在此時才顯示拖曳提示。
  4. 第 15 秒必須出現第一次雜兵團衝撞，給予第一個明確的「我的累積有用」回饋。
  5. 第一關的 Boss 必勝，且結算畫面立刻給金幣與第一個可購買的升級 — 在玩家離開之前就把 meta 層亮出來。

§ 6三階段路線

順序是刻意的：先讓遊戲本身成立，再讓它可被測量與擴充，最後才接通路。 反過來做（先接 SDK 再修數值）會讓你用真實流量去驗證一個已知有問題的迴圈。

階段 一

止血

約 1–2 週 · 不改架構

目標：讓「玩得好」與「玩得爛」產生不同結局。這階段不碰模組拆分，全部在現有單檔內完成。

  • Boss 血量與兵力脫鉤，傷害改為次線性（P0·1）
  • 雜兵團改百分比損耗、乘法閘門稀有化、過關繼承設上限（P0·2）
  • 閘門改為「兩邊都是好處」，移除綠 / 紅二分（P0·3）
  • 加入 save.js，持久化最高紀錄 / 關卡 / 靜音（P0·4）
  • 數字格式化（1.2萬 / 3.4M）、修正勝利後 700 ms 空窗、AudioContext.resume()

驗收：手動玩到第 8 關，兵力峰值不超過 5,000；至少要能在第 5 關之後因為選錯門而輸掉一場。

階段 二

產品化

約 3–4 週

目標：把調校從手感變成數據，並補上 hybrid-casual 的骨架。

  • 依 § 4 拆分模組，數值集中到 balance.js，導入固定步長與帶種子 PRNG
  • 建立 balance.test.js，把本報告的模擬變成專案內建的回歸測試
  • 精靈圖預繪 + 三段 LOD（P1·5）— 同時解決效能與「成長看不見」
  • 金幣 + 永久升級樹 + 兵種解鎖（§ 5）
  • 接入分析埋點與獎勵式影片的四個佈點（P1·6），先用 none.js 假實作跑通流程
  • 重寫前 30 秒（§ 5）

驗收：npm test 可在無瀏覽器環境跑完八關曲線斷言；低階 Android 上穩定 60 fps。

階段 三

上通路

約 5–8 週

目標：用真實流量驗證留存曲線，取得第一筆收入。

  • 實作 platform/ adapter，接 CrazyGames（可先走 Basic Launch，兩週試水不需完整 SDK）與 Poki（需申請邀請）
  • 加入 PWA manifest + Service Worker + Open Graph 標籤
  • 移除 window.__game，加基本的分數合理性檢查
  • 用同一份程式碼輸出 playable ad 版本 — 30 KB 的體積讓這幾乎是免費的
  • 依實際 D1 / D7 決定是否加入每日挑戰與免廣告 IAP

驗收：取得第一份真實留存曲線，對照下表判斷是否值得投入階段四。

§ 7不建議做的事

  1. 不要換成 Three.js 或 Unity WebGL。畫面確實會好看，但 30 KB 會變成 5–15 MB， 直接踩掉 Poki 的 8 MB 門檻與 CrazyGames 手機首頁位的 20 MB 門檻，並犧牲冷啟動速度 — 也就是犧牲掉這個專案目前唯一的結構性優勢。真要提升畫面，先做精靈圖與 LOD（P1·5）， 效果好、成本低，而且順帶解決效能問題。
  2. 不要增加操作複雜度。跳躍、衝刺、多車道都會拉高學習成本，卻不解決「沒有選擇」這個真正的問題。 深度應該來自閘門的決策與兵種，而不是手指。
  3. 不要先做 IAP 商城。在 D1 留存站上 25% 之前，付費設計沒有作用對象。 第一個 IAP 應該是「免廣告」，且要等到獎勵式影片跑順了再上。
  4. 不要在修好經濟迴圈之前買量。美國 Android 休閒 CPI 已達 $1.5–3.5 且持續上漲； 把錢投進一個第 6 關就失去挑戰性的迴圈，只會用比較貴的方式確認它壞了。
